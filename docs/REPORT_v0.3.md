## 4. 실제 시간으로 얼마나 걸리나 — 기본안

브리프에서 보류였던 항목이라 시뮬레이션으로 정했다(봇 12종 → 조정 3회). 자세한 건 `docs/GDD.md` §1.1, `docs/BALANCE_CHANGELOG.md`.

| 이정표(봇 기준 — 사람은 약 2배로 본다) | 하루 4번 접속 | 하루 2번 접속 |
|---|---|---|
| 첫 세입자 | 7분 | 7분 |
| 첫 토박이 | 24분 | 12시간 |
| 첫 유지 | 15시간 | 2.5일 |
| 첫 거물 | 1일 | 3.5일 |
| 성채 회관 | 2일 | 6일 |
| 마지막 목표 | **6일** | **12.5일** |

- 처음 돌렸을 때는 마지막 목표가 **1일 / 3.5일**이었다. 경제 시계가 실제 하루에 26~45경제일씩 흘러서, 세수·계약·연구만으로는 하루 이틀이면 끝까지 갔다.
- 그래서 **실제 시계로 도는 탐험을 관문으로** 삼았다: 승급 자재를 4 / 30 / 40 / 80으로 올리고, 설비 부품(거물 승급 3개)을 원거리 탐험이 주게 하고, 건재상은 비싼 보조로 줄였다. 첫 접속 15분의 속도는 건드리지 않았다.
- 짧게 자주 접속하며 근거리만 도는 봇은 10일 안에 마지막 목표에 못 닿았다(부품 부족). 원거리가 부품을 준다는 걸 지도에 금색 표시로 넣었다.

## 5. 확인한 것 / 못 한 것

**확인함**
- 첫 접속 흐름을 실제 터치 입력으로 끝까지: 오프닝 → 집 8채 → 좌판·빗물받이 둘·텃밭 → 탐험 보내기 → 첫 승급(목재) → 수령 → 교역·초 공방 → 2층. 한 줄로 다시 돌릴 수 있다(`docs/INTEG_NOTES.md`).
- 화면 전부를 실제 데이터로: 탐험·목표·연구·정책·경제·교역·들여다보기·알림 이동·미접속 요약·단속.
- 봇으로 28~40경제일(다섯 계층, 5층)까지 화면 오류 없이.
- 웹 빌드: 폰 크기(412×915)·터치로 부팅, 오프닝, 끌어 칠하기, 시설 배치, 탭 5개, 회전·확대. 콘솔 오류 없음, 한글 정상.
- 시뮬레이션 시험 전부 통과. 속도용 캐시가 맞는지 보는 비교 시험을 추가했다: 캐시를 켠 쪽과 끈 쪽에 같은 무작위 명령을 넣고 상태 전체를 비교 — 씨앗 20개 × 30경제일, 명령 약 6,300개, 저장·불러오기 98회, 미접속 정산 61회에서 일치(그 과정에서 찾은 원인 2개는 고쳤다, §8).
- 탐험으로 거래처 발견 → 교역 제안에 뜨는 것(규칙 층에서 확인).

## 6. 내가 정한 것 — 승인이 필요하다

전부 `godot/data/**.json`의 숫자·문구라 뒤집기 쉽다. 디렉터 수준의 가정은 `docs/ASSUMPTIONS_AND_EXPERIMENTS.md`(A1~A22)에 "무엇을 / 왜 / 뒤집는 곳"으로 적었다. 이번에 새로 정한 큰 것:

1. **실시간 속도는 탐험 자재·부품이 정한다**(A16). 시계(접속 10분 = 1경제일, 미접속 0.25배·8시간)는 그대로.
2. **승급 자재 4 / 30 / 40 / 80 + 거물 부품 3, 문턱 토박이 300 · 유지 120 · 거물 150, 회관 = ₩25,000 + 세 자재 각 150 + 부품 20**(A17). 위 표의 속도를 만드는 수치.
3. **근거리 탐험은 세 계열 모두 1분에 1개**(A18) — 어느 자재도 정답이 아니게.
4. **설비 부품은 원거리 탐험이 꼭 하나, 옛 발전소는 3~4개. 건재상은 비싼 보조**(A19).
5. **전파사(라디오)는 토박이 300명 뒤에**(A20) — 첫 유지가 너무 일찍 나오지 않게.
6. **시작 재고에 헌 옷 8·초 10** — 첫 승급(자재 고르기)을 교역 없이 첫 접속에 맛보게. 약 한 시간 뒤 떨어지면 교역으로 이어진다.
7. **오프닝은 조작만 가르치고, 그 뒤는 단계 목표가 안내**한다(방법 한두 줄 + 바로 가는 버튼).
8. **목표 문구에 승급 조건을 그대로**(A22) — 예: "비누·의원(무면허 치과)을 갖춘 만실 세입자 집".
9. **계약은 경제 시계**(A6, 이전 결정 유지) — 소비와 같은 속도로 흘러야 재고가 맞는다.
10. **연구·정책 트리**(A11, Jin 요청으로 추가)의 내용 — 연구 12개·정책 6개의 이름과 효과는 내가 썼다.

작업 에이전트가 정한 세부 결정(번호와 이유): `docs/SIM_NOTES.md` §7(37개), `docs/VIEW_NOTES.md` §4(15개), `docs/UI_NOTES.md` §3(약 50개), 수치 변경 이력은 `docs/BALANCE_CHANGELOG.md`.

## 7. Jin이 골라야 할 것

**① 후반에 쌓이는 돈** — 지금은 10일째 약 ₩500만이 쌓이고 쓸 곳이 없다(연구·회관·승급에 다 써도 남는다). 후반 놀이의 성격을 정하는 결정이라 남겨 뒀다.
1. **상납금**: 금고가 커질수록 경찰·삼합회·구청이 떼어 간다. 정책 "뒷돈"의 수준을 고르면 단속 위험과 맞바꾼다. 풍자와 맞고, 구현이 작다. (내 추천)
2. **돈으로 시간을 산다**: 건재상에 비싼 대량 주문을 연다. 돈의 쓸모는 생기지만 탐험의 관문이 약해진다.
3. **반복 구매형 명소**: 회관 증축·기념물을 점점 비싼 값에 계속 사서 행복·세수를 올린다. 새 콘텐츠와 외관 작업이 든다.
4. **살림을 빡빡하게**: 상위 계층 세율을 내리고 상위 시설 유지비를 올려 순이익 자체를 줄인다.
5. 그대로 둔다(자유 모드의 돈은 장식).

**② 진행 속도** — 기본안은 마지막 목표까지 봇 기준 6일 / 12.5일(사람은 그 두 배쯤).
1. 기본안 그대로.
2. 더 길게(약 2배) — 처음 컨셉의 "한 달"에 가깝게.
3. 더 짧게 — 조정 전 수준(1일 / 3.5일). 검토에는 편하지만 탐험이 관문 역할을 못 한다.

**③ 미접속 정산 시간** — 주거 1,000채 도시에서 8시간치 정산이 PC 0.9초, 폰에서는 5~9초로 추정된다(실측 아님).

2. 상한을 4시간으로 줄인다.
3. 큰 도시만 더 거친 간격으로 계산한다(결과 오차가 조금 커진다).

**④ 그래픽 올리기** — "더 디테일한 그래픽"은 게임성 다음이라 이번엔 손대지 않았다.

## 8. 이번에 잡힌 큰 문제(고쳤다)

- 폰·웹에서 집을 칠할 때 **첫 획이 지우개가 되던 것**(터치를 흉내 낸 마우스 입력이 먼저 와서 같은 칸이 두 번 눌렸다).
- **집을 먼저 칠하고 시설을 나중에 지으면 주민이 집당 1명에서 안 늘던 것** — 속도용 캐시가 낡은 값을 썼다. 봇은 짓는 순서가 달라 못 잡았고, 실제 화면으로 눌러 보다가 찾았다. 그래서 캐시를 켠 쪽과 끈 쪽에 같은 무작위 명령을 넣어 결과를 비교하는 시험을 추가했다.
- 승급 창의 버튼이 화면 밖으로 밀리던 것, 위 띠의 돈 표시가 겹치던 것, 오프닝 대사를 넘기려는 터치가 아래 집을 열던 것.
- 목표 문구가 실제 승급 조건과 달랐던 것(네 곳).
- 캐시 비교 시험이 하나 더 찾았다: 자정·저장 때의 반올림 뒤에 일부 주거가 다시 계산되지 않아 값이 끝자리에서 어긋나고, 드물게 주민이 떠나는 시점이 한 스텝 달라졌다.
- 성능: 주거 1,000채에서 한 스텝 약 120ms → 약 8ms(다른 작업과 CPU를 나눠 쓸 때는 12~13ms로 측정), 8시간 미접속 정산 약 70초 → 약 0.9초.
- "목재이(가) 모자란다" 같은 조사, 돈의 천 단위 쉼표, 화면에 남아 있던 개발 메모.
